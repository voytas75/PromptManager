## Decyzja / priorytet

Najpierw gwarancja *invalid request = no chain execution*, następnie jednoznaczny JSON w ścieżce `prompt-history` i dopiero potem wejście/wyjście `prompt-add` (osobna decyzja kontraktowa: `--json` to historyczny input, nie można mu po cichu zmienić znaczenia). Nie deklarować całego CLI „agent-ready”; obecne izolowane komendy mają różne kontrakty. Alternatywa: oddzielny adapter/API agenta; wrócić do niej tylko po obserwowalnej potrzebie równoległych sesji lub zdalnego dostępu, której lokalny CLI nie spełnia.

## Granice / do weryfikacji w osobnym zakresie

- Parser/startup nie gwarantują ustrukturyzowanego błędu dla każdego `--json`/`--result-json`; `--result-json` daje tylko agregaty bez identyfikatorów utworzonych promptów. Importer aktualizuje całe rekordy po nazwie; to nie jest bezpieczny zamiennik promocji draftu ani edycji pojedynczego pola.
- `prompt-chain-run` gwarantuje brak wykonania dla przetestowanych konfliktów trybu wyjścia, nie dla dowolnego błędu. `prompt-history` i `prompt-add` nadal inicjalizują managera; opcjonalne integracje i nietypowe warningi nie są ujęte w maszynowym kontrakcie. Nie twierdzić, że cały CLI jest agent-ready lub bez efektów ubocznych.
- Osobny adapter/API dla współbieżnych agentów lub zdalnego dostępu dopiero po potwierdzeniu takiej potrzeby. Wznowić plan tylko przy konkretnym zgłoszeniu błędu parser/startup, potrzeby ID receipt, bezpiecznej promocji draftu lub izolacji sesji.
