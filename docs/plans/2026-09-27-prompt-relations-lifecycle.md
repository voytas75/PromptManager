Status: S1–S3 locally verified; S4 impact UI deferred. Product authority: `docs/product-ssot.md`. Baseline: `master` at `7fb0e5c3c071d23a0553b6d87e136ec6adbecd7e` on 2026-09-27. This plan is not a second product SSOT.

## Decision and boundary

Keep stable prompt UUIDs as relation targets; do not introduce source-version pinning or a graph editor. A fork is a separate prompt; its source relation, `related_prompts` metadata, and prompt-chain steps are distinct dependency kinds. `is_active=False` retains ID, body and relations; it is not deletion. A tag is not a lifecycle state. The existing version history remains untouched; removal is outside this campaign.

**Deletion policy:** physical deletion of X is refused when any *other* stored prompt forks from X, has the canonical UUID of X in `related_prompts`, or any chain step references X, regardless of dependent active state. A self-reference also blocks deletion until deliberately removed. S1 reports bounded dependency kinds (not counts or dependent IDs), never prompt bodies or raw invalid metadata. Structurally corrupt catalog rows fail closed; unrelated legacy non-UUID references still appear in doctor but do not block an otherwise independent deletion. Deactivation is the reversible alternative. Deleting an unreferenced prompt remains possible. New references must be validated at the write boundary in a separate bounded slice; this first guard alone cannot prevent every racing or out-of-band malformed import.

**Activity policy (owner confirmed 2026-09-27):** inactive records retain their UUID, body and relationships, remain inspectable/addressable by ID and in doctor checks, and may be explicitly included in discovery. Ordinary discovery should not suggest them by default. A deliberate run (including a chain step) or fork of inactive X must refuse before contacting a provider. Chain *definitions* remain valid with an inactive step; reactivation uses the same ID. Execution and fork entrypoints recheck canonical SQLite activity; a status change between the last check and provider contact remains a race. No implicit historical-version pinning.

**Precedence:** preserve safety before convenience. Confirm relation integrity on disposable data only; no changes to the Windows/user catalog. Do not alter `ON DELETE CASCADE` as the primary remedy; application-level guard must run before touching Chroma/cache and SQLite must recheck in a write transaction. Keep rollback-fork cleanup and draft delete consistent with the same protection. Cross-store atomicity is not implied by the guard. The owner subsequently authorized commit and push after local review and gates; no provider or Windows/user-catalog writes were authorized.

## Current doubts / stop conditions

- S1 holds a SQLite write transaction across dependency inspection, index attempt, and catalog delete. A vector mutation followed by failure still needs an explicit cross-store recovery; the typed partial outcome is not an atomic rollback guarantee.
- The separate draft CLI deletion path now participates in the same dependency guard; keep its bounded JSON failure contract in subsequent changes.
- References added via JSON metadata/import after guard preflight can race or bypass canonical validation. Do not promise universal integrity until write-path coverage is proven.
- S3 covers tested run/fork/benchmark/GUI paths and common default discovery, including preflight of all chain steps. A standalone CLI does not evict another process's cache; execution/fork checks read SQLite afresh. Deactivation can race between this check and a provider call; do not claim atomic exclusion. Semantic search filters the returned top-k Chroma candidates, so inactive candidates can shorten a result page; explicit inactive search is not guaranteed exhaustive.
